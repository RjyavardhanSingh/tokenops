Architecture note

TokenOps trust boundaries

TokenOps is runtime cost governance for client agents — where their process ends and the control plane's takes over, and what crosses the network in between.

Trust model

client agent process
No boundary here. The client's own agent code is what's being governed — Chronicle wraps every tool and LLM call it makes to record input/output, and calls the TokenOps hook inline before and after each one. Nothing about this step touches the network.
network
The only crossing point. Chronicle ships the call trace to the control plane; the hook separately pulls a budget signal and gets an authorize/deny back — two calls out, same destination, same credential.
control-plane container
One Docker image, three roles. The API process, the policy/ledger UI, and SQLite all ship together. The UI has no private path to the database — it's a client of the same API the hooks call, which is where policies are read and edited.
auth
One tenant-level admin API key, generated the first time a user registers the control plane against their cloud or infra. Every hook and the UI present that same key today — there's no per-agent or per-user identity yet, so anyone holding it can read the ledger and rewrite policy.
